# Cubehelix Studio — Remaining Backlog Handoff

## Project context

Cubehelix Studio is a TypeScript + Python tool for designing cubehelix color palettes. Repo at `/home/thiebes/wsl-repos/lumenfast`. Two packages and one app share the math:

- `packages/core` — TypeScript implementation of cubehelix ([cubehelix.ts](packages/core/src/cubehelix.ts)), lightness curves ([lightness-curve.ts](packages/core/src/lightness-curve.ts)), chroma envelope ([chroma-envelope.ts](packages/core/src/chroma-envelope.ts)), sequential sampling, contrast, format, role-based palettes ([roles.ts](packages/core/src/roles.ts)), and palette exports ([exports.ts](packages/core/src/exports.ts)). Tests via vitest.
- `packages/python` — Python mirror (`cubehelix_studio/`) with the same math + matplotlib adapter. Tests via pytest.
- `apps/web` — Vite + React studio app. Renders gradient strip, swatch row, 3D cube visualization (three.js + r3f), parameter controls, share-link URL state, and an export panel.

**Parity discipline.** TS and Python must produce numerically identical output (< 1e-12 per channel). A fixture at `fixtures/parity.json` is generated by `pnpm fixture:gen` from the TS implementation; the Python parity test asserts agreement. Any math change requires regenerating the fixture and verifying both test suites pass.

### Mental model

- **The RGB cube is the workspace.** `(0, 0, 0)` is black, `(1, 1, 1)` is white. Coordinate system; doesn't change.
- **The helix's endpoints are anchored at the black and white corners.** Everything else about the helix is parameter-controlled:
  - `start` — hue offset at the black anchor
  - `rotations` — number of hue turns from black to white
  - `saturationMin`, `saturationMax`, `chromaPeak`, `chromaWidth`, `chromaFloor` — how far the helix bulges from the cube diagonal at each point along it
  - `lightnessCurve` (power / sigmoid / bezier) — how lightness rises along the curve, parameterized by `u ∈ [0, 1]`. It does not change which colors lie on the helix, only how the parameter is paced.
- **The lightness axis bounds clip the helix to a sub-arc.** `[lightnessAxisMin, lightnessAxisMax]` selects the portion whose lightness output lies inside that window — they don't reshape the helix. The visible palette traverses only the surviving sub-arc, so narrower bounds expose fewer hue cycles.

### Math

```text
tEff   = reverse ? 1 - t : t
uMin   = invertLightnessCurve(curve, lightnessAxisMin)
uMax   = invertLightnessCurve(curve, lightnessAxisMax)
u      = uMin + (uMax - uMin) · tEff                       // helix parameter
fraction = evaluateLightnessCurve(curve, u)
angle  = 2π · (start/3 + rotations · u + 1)
sat    = saturationMin + (saturationMax − saturationMin) · tEff
amp    = sat · chromaEnvelope(fraction, peak, width, floor)
r,g,b  = fraction + amp · projection(angle)                 // BT.601 helix coefficients
```

`evaluateLightnessCurve(curve, u)` dispatches on curve.kind: `power(t^gamma)`, normalized `sigmoid(steepness, midpoint)`, or `bezier(p1, p2)` solved by Newton + bisection. `invertLightnessCurve` is its monotonic inverse, computed by bisection.

`chromaEnvelope(f, peak, width, floor)` is a beta-shape `f^a · (1−f)^b` peak-normalized to 1, lifted by `floor`, scaled by a calibration constant 0.125 such that defaults `(0.5, 1, 0)` collapse to the original `f·(1−f)/2`.

### `CubehelixParams`

```ts
type LightnessCurve =
  | { kind: "power"; gamma: number }
  | { kind: "sigmoid"; steepness: number; midpoint: number }
  | { kind: "bezier"; p1: [number, number]; p2: [number, number] };

interface CubehelixParams {
  start: number; // [0, 3], periodic
  rotations: number; // unbounded; turns over the full lightness axis
  saturationMin: number; // [0, ∞); chroma amplitude at tEff = 0
  saturationMax: number; // [0, ∞); chroma amplitude at tEff = 1; collapses to a single saturation when equal to saturationMin
  lightnessCurve: LightnessCurve;
  lightnessAxisMin: number; // [0, 1]
  lightnessAxisMax: number; // [0, 1], must be ≥ lightnessAxisMin
  chromaPeak: number; // [0, 1]; lightness location of peak chroma
  chromaWidth: number; // [0.1, 5]; sharpness of peak (smaller = narrower)
  chromaFloor: number; // [0, 1]; baseline envelope at endpoints
  reverse: boolean;
}
```

**URL state** ([apps/web/src/lib/url-state.ts](apps/web/src/lib/url-state.ts)). Round-trippable, default-omitting. Numeric keys: `start`, `rotations`, `lightnessAxisMin`, `lightnessAxisMax`, `chromaPeak`, `chromaWidth`, `chromaFloor`. Saturation keys: `saturation` is emitted when `saturationMin === saturationMax`; otherwise the split form emits `saturationMin` / `saturationMax`. On decode, a single `?saturation=` sets both ends, and explicit `saturationMin` / `saturationMax` keys override. Curve keys: `lightnessCurve` (omitted when `power`), `gamma`, `sigmoidSteepness`, `sigmoidMidpoint`, `bezier1x` / `bezier1y` / `bezier2x` / `bezier2y`. Plus `reverse` (1/0) and `swatchCount`. Legacy `?gamma=…` and `?saturation=…` URLs decode cleanly. New keys must follow this pattern (camelCase, omitted when at default).

### Other architectural notes worth knowing

- The 3D cube visualization ([apps/web/src/components/CubeVisualization.tsx](apps/web/src/components/CubeVisualization.tsx)) renders the full underlying helix by overriding `lightnessAxisMin: 0`, `lightnessAxisMax: 1`, `reverse: false` in `fullHelixParams`. Cross-sections at out-of-range u are ghost-rendered (white dashed lines). In-range out-of-gamut samples render as colored tube clamped to the cube wall AND ghost line outside.
- `PolylineCurve.getPointAt` is overridden to bypass `THREE.Curve`'s arc-length re-sampling — `TubeGeometry`'s cross-sections must align with input sample indices for the per-sample colors to land at the right vertices. Don't undo this.
- Vertex colors written by `buildColoredTube` are linear-encoded via `srgbToLinear`. `THREE.BufferAttribute` does not have a `colorSpace` property in the pinned three.js; manual linearization is the correct pattern.
- Saturation cap (`saturationCap` in `cubehelix.ts`) is the 95th percentile of per-sample S_exit values. The slider's max in `ParamControls` sweeps `start` over 24 values and takes the worst-case cap, so the slider stays stable as the user spins the start hue.
- The cube viz scene is shifted by `[-0.5, -0.5, -0.5]` so the cube is centered at world origin and `OrbitControls.target = (0, 0, 0)` orbits the centroid.
- The starting-hue wheel ([StartingHueWheel.tsx](apps/web/src/components/StartingHueWheel.tsx)) is a static reference rendered at `rotations = 0`, `lightnessAxisMin = lightnessAxisMax = 0.5`, `saturationMin = saturationMax = 2`. Each segment shows the abstract hue at that `start`, peak-normalized so all hues are equally vivid. The pointer color does not depend on the user's other parameters; an inline `?` popover in the panel explains the relationship between the picker hue and what the gradient actually looks like.

### Control panel structure

The parameter panel is a stack of collapsible sections (native `<details>`):

- **Hue** (open) — Starting Hue (wheel + numeric), Hue Rotations
- **Lightness** (collapsed) — Lightness Curve (radio: Power / Sigmoid / Bezier with sub-controls), Lightness Axis
- **Chroma** (open) — Saturation, Peak Position, Chroma Width, Chroma Floor
- **Output** (collapsed) — Reverse, Swatches

`Reset` lives in the page header alongside `Share` (link icon) and `About`. Reset returns params + swatchCount to defaults and resets the cube camera.

## Stage 3 — Diverging cubehelix

**Goal.** Two-sided palette where lightness rises from a lower extreme to a midpoint pivot, then falls back to an upper extreme (or vice versa). Each half is a cubehelix with potentially different rotation count. Examples: red-to-white-to-blue with hue rotations on each side. None of the surveyed cubehelix implementations ships diverging; this is a differentiator.

**Math.** Define a `pivot ∈ (0, 1)` t-value. For `t ∈ [0, pivot]` use one cubehelix from `(start, rotationsLower)` with lightness from `lightnessLower` to `lightnessPeak`. For `t ∈ [pivot, 1]` mirror: lightness from `lightnessPeak` back down to `lightnessUpper`, with hue from `startUpper` (often `start + offset`) and `rotationsUpper`.

Several flavors are possible:

- Symmetric: same rotations both sides, same outer lightness, hue mirrors around the pivot.
- Asymmetric: each side has independent rotations, lightness extents, and possibly different starting hues.

Recommend asymmetric for flexibility, with optional "symmetric" preset.

**Mode.** Add a top-level `mode: "sequential" | "diverging"`. In diverging mode, expose new fields and hide `lightnessAxisMin`/`lightnessAxisMax` (which become per-half) and `rotations` (which becomes `rotationsLower` / `rotationsUpper`).

**Math (concrete suggestion).**

```text
diverging:
  if t ≤ pivot:
    s = t / pivot                     // 0 .. 1 within lower half
    apply cubehelix with:
      rotations = rotationsLower
      lightness axis = [lightnessLower, lightnessPeak]
      curve = lightnessCurveLower (defaulting to mirror of upper)
      start = start
  else:
    s = (t − pivot) / (1 − pivot)     // 0 .. 1 within upper half
    apply cubehelix with:
      rotations = rotationsUpper
      lightness axis = [lightnessPeak, lightnessUpper]   // descending if peak > upper
      start = startUpper
```

The lightness axis bounds should be configured so the lower half's `t = pivot` evaluates to the peak, and the upper half's `t = pivot` also evaluates to peak — ensuring continuity at the pivot.

For reverse divergence (peak in middle is dark, ends are light), simply swap which extreme is "peak" vs. "outer."

**Type changes.**

```ts
interface CubehelixParams {
  // ...
  mode: "sequential" | "diverging";
  pivot?: number; // [0, 1], required when mode = "diverging"
  rotationsLower?: number; // when diverging
  rotationsUpper?: number; // when diverging
  lightnessPeak?: number; // when diverging
  lightnessLower?: number; // when diverging (replaces lightnessAxisMin)
  lightnessUpper?: number; // when diverging (replaces lightnessAxisMax)
  startUpper?: number; // when diverging; defaults to start + 0.5 (180° offset) if absent
}
```

Keep the `mode = "sequential"` path 100% backward compatible (use existing `rotations`, `lightnessAxisMin`, `lightnessAxisMax` etc.).

**URL keys.** `mode`, plus `pivot`, `rotationsLower`, `rotationsUpper`, `lightnessPeak`, `lightnessLower`, `lightnessUpper`, `startUpper`. Default-omitted in sequential mode.

**UI.** A mode selector at the top of `ParamControls.tsx`. In diverging mode, the panel reorganizes to show both sides' parameters. Consider a visual "fold" indicator on the gradient strip showing the pivot.

**Saturation cap.** Recompute per-half (each half has its own envelope and lightness range) and take the worst-case cap.

**Cube viz — two-cube layout.** In diverging mode, render two RGB cubes positioned so each half's pivot point coincides at a single shared location in world space. Each cube extends back toward its own dark-corner endpoint. The two helix-tube paths meet at that shared point, making the divergent structure read at a glance.

- Anchor point: `(lightnessPeak, lightnessPeak, lightnessPeak)` if `startUpper - start` keeps the pivot near the diagonal; in general, the pivot's actual RGB coordinates from the cubehelix evaluation.
- If `lightnessPeak = 1`, the shared point is the white corner of both cubes (clean visual).
- For any other peak, the shared point is interior and the cubes overlap geometrically. That's fine and arguably informative — the overlap region is where both halves can reach the same colours.
- Optional "anchor mode" toggle: shared-point view vs. side-by-side view, in case users find the overlap confusing.
- Each cube's wireframe and gamma-axis indicators render independently; the helix tube is two segments (lower half + upper half) meeting at the anchor.

**Lightness ramp visualization (`GammaBar`)** needs to show the diverging shape (rises to peak, falls back).

**Gradient strip.** Render normally — the diverging palette is still a `t ∈ [0, 1]` ramp, just one whose lightness profile is non-monotonic.

**Tests.** Sequential mode is unchanged. Diverging mode: continuity at pivot (cubehelix output approaches the same value as `t → pivot` from below and above). Endpoints respect `lightnessLower`/`lightnessUpper`. Hue waypoints (if combined with diverging) — out of scope for now, document as future work.

**Files.** Pretty much everything: core math, types, defaults, URL state, `ParamControls`, `GradientStrip`, `GammaBar`, `CubeVisualization` (sample generation + two-cube layout), Python mirror, fixture generator, all tests.

## Deferred / out of scope

These came up in the field-survey of other cubehelix implementations; documenting the decision so future contributors don't relitigate.

- **Oklab / CIELab perceptually-uniform reformulation.** A second curve family where lightness is monotonic in perceptual space rather than BT.601 luma. Substantial scope (new helix coefficients, new gamut-cap math, new parity entries, deciding whether it's a parameter or a sibling function). Worth revisiting if user demand surfaces.
- **First-class Cubehelix colour space** (RGB ↔ cubehelix coordinates, `.brighter()`/`.darker()`, opacity channel — d3-style). Different framing from "design a palette, then export"; would inflate the API surface significantly.
- **Per-channel RGB→luma weight tuning** (Thies's `wr`/`wg`/`wb` with NTSC/PAL/HDTV presets). Scientific-imaging niche; off-mission for a UI palette tool.
- **Split gammas** on rotation rate and amplitude (Thies `gamma_rot`, `gamma_amp`). The lightness-curve selector and chroma envelope cover the same design space more cleanly.
- **Per-channel helix distortion** (Thies expert mode `kr/og` etc.). Explicitly experimental even in the original.
- **d3-style "interpolate between two arbitrary colours through cubehelix"**. Different framing; users who need it can reach for d3.

## Cross-cutting expectations for any agent picking this up

- Read the current `cubehelix.ts` and `cubehelix.py` first; the math is short and there are subtle invariants (the helix is a fixed object in cube space, parameterized by `u`; lightness axis bounds clip it to a sub-arc; rotations counts turns over the full axis, not the visible window).
- Before changing math: write a numeric test that exercises the change, then implement, then regenerate the parity fixture (`pnpm fixture:gen`).
- Keep `DEFAULT_CUBEHELIX_PARAMS` such that defaults reproduce the existing visual output bit-for-bit on the parity fixture's existing entries. New fixture entries should be ADDED for new parameters, not modify existing ones.
- URL state encoding: every new field must omit-on-default and round-trip via the existing `encodeAppState`/`decodeAppState`.
- All changes must keep all three test suites green: `pnpm -F @cubehelix-studio/core test`, `pnpm -F web test`, and `(cd packages/python && uv run pytest)`. Plus `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, and `pnpm build`.
