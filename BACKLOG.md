# Cubehelix Studio — Remaining Backlog Handoff

## Project context

Cubehelix Studio is a TypeScript + Python tool for designing cubehelix color palettes. Repo at `/home/thiebes/wsl-repos/lumenfast`. Two packages and one app share the math:

- `packages/core` — TypeScript implementation of cubehelix ([cubehelix.ts](packages/core/src/cubehelix.ts)), sequential sampling, contrast, format, role-based palettes ([roles.ts](packages/core/src/roles.ts)), and palette exports ([exports.ts](packages/core/src/exports.ts)). Tests via vitest.
- `packages/python` — Python mirror (`cubehelix_studio/`) with the same math + matplotlib adapter. Tests via pytest.
- `apps/web` — Vite + React studio app. Renders gradient strip, swatch row, 3D cube visualization (three.js + r3f), parameter controls, share-link URL state, and an export panel.

**Parity discipline.** TS and Python must produce numerically identical output (< 1e-12 per channel). A fixture at `fixtures/parity.json` is generated by `pnpm fixture:gen` from the TS implementation; the Python parity test asserts agreement. Any math change requires regenerating the fixture and verifying both test suites pass. Fixture is currently at version: 4.

**Math (current state).** [cubehelix.ts:13](packages/core/src/cubehelix.ts#L13):

```text
tEff   = reverse ? 1 - t : t
uMin   = lightnessMin^(1/gamma)
uMax   = lightnessMax^(1/gamma)
u      = uMin + (uMax - uMin) * tEff
fraction = u^gamma
angle  = 2π · (start/3 + rotations · tEff + 1)        // tEff, NOT u (Green canonical)
amp    = saturation · fraction · (1 − fraction) / 2
r,g,b  = fraction + amp · projection(angle)            // BT.601 helix coefficients
```

Default lightness `[0, 1]` and `gamma = 1` makes `u = tEff = fraction`, so all three forms collapse and existing palettes are unchanged.

`CubehelixParams`:

```ts
interface CubehelixParams {
  start: number;        // [0, 3], periodic
  rotations: number;    // unbounded; visible turns over t ∈ [0, 1]
  saturation: number;   // [0, ∞)
  gamma: number;        // (0, ∞), slider range [0.5, 2]
  lightnessMin: number; // [0, 1]
  lightnessMax: number; // [0, 1], must be ≥ lightnessMin
  reverse: boolean;
}
```

**URL state** ([apps/web/src/lib/url-state.ts](apps/web/src/lib/url-state.ts)). Round-trippable, default-omitting. Keys: `start`, `rotations`, `saturation`, `gamma`, `lightnessMin`, `lightnessMax`, `reverse` (encoded as 1/0), `swatchCount`. New keys must follow this pattern (camelCase, omitted when at default).

**Other architectural notes worth knowing:**

- The 3D cube visualization ([apps/web/src/components/CubeVisualization.tsx](apps/web/src/components/CubeVisualization.tsx)) renders the full underlying helix by overriding `lightnessMin: 0`, `lightnessMax: 1`, `reverse: false` in `fullHelixParams`. Cross-sections at out-of-range u are ghost-rendered (white dashed lines). In-range out-of-gamut samples render as colored tube clamped to the cube wall AND ghost line outside.
- `PolylineCurve.getPointAt` is overridden to bypass `THREE.Curve`'s arc-length re-sampling — `TubeGeometry`'s cross-sections must align with input sample indices for the per-sample colors to land at the right vertices. Don't undo this.
- Vertex colors written by `buildColoredTube` are linear-encoded via `srgbToLinear`. `THREE.BufferAttribute` does not have a `colorSpace` property in three.js 0.184; the auditor's recommendation to set it is a no-op. Leave the manual linearization in place.
- Saturation cap (`saturationCap` in `cubehelix.ts`) is the 95th percentile of per-sample S_exit values. The slider's max in `ParamControls` sweeps `start` over 24 values and takes the worst-case cap, so the slider stays stable as the user spins the start hue.
- The cube viz scene is shifted by `[-0.5, -0.5, -0.5]` so the cube is centered at world origin and `OrbitControls.target = (0, 0, 0)` orbits the centroid.

**Wheel feature in flight, uncommitted.** A starting-hue color wheel (`StartingHueWheel.tsx`, modifications to `App.tsx`, `ParamControls.tsx`, hue-control CSS in `styles.css`) was built by another agent in parallel and is currently uncommitted on main. Don't conflict with those files until that work is committed.

## Stage 2a — Lightness curve generalization

**Goal.** Replace the single gamma knob with a choice of monotonic lightness curves: power (current), sigmoid, bezier. As `t ∈ [0, 1]` sweeps, the lightness ramp `fraction(t)` should be governed by the chosen curve rather than always being a power function. The chroma envelope and angle math stay unchanged.

**Math.** Currently `fraction = u^gamma` where `u = uMin + (uMax − uMin) · tEff`. Generalize to:

```text
fraction = lerp(lightnessMin, lightnessMax, curve(tEff))
```

where `curve: [0, 1] → [0, 1]` is monotonically increasing and `curve(0) = 0`, `curve(1) = 1`.

**Curve types:**

- `power(gamma)`: `curve(t) = t^gamma`. Defaults reproduce current behavior at `gamma = 1`.
- `sigmoid(steepness, midpoint)`: a normalized logistic, e.g. `curve(t) = (sigm(steepness · (t − midpoint)) − sigm(−steepness · midpoint)) / (sigm(steepness · (1 − midpoint)) − sigm(−steepness · midpoint))`. Steepness controls slope at the midpoint; midpoint shifts the inflection. Larger steepness emphasizes mid-tones less and dark/light extremes more.
- `bezier(p1, p2)`: a cubic Bézier with endpoints `(0, 0)` and `(1, 1)` and two control handles `p1, p2 ∈ [0, 1]²`. Constrain handles so the curve is monotonic; reject or clamp inputs that would cause overshoot/inversion. Reasonable approach: enforce `0 ≤ p1.x ≤ p2.x ≤ 1` (handle x-coordinates monotonic) — sufficient for monotonic y under normal handle ranges. Document the constraint in a code comment.

**Note on u vs fraction.** The existing math uses `u = lerp(uMin, uMax, tEff)` and `fraction = u^gamma` separately because `uMin` and `uMax` are derived by inverting the lightness range under gamma. With curves other than power, the inversion is not closed-form — define lightness range directly on the lightness output: `fraction = lerp(lightnessMin, lightnessMax, curve(tEff))`. This is cleaner and avoids gamma-inverse hacks. Verify behavior matches current at `power(gamma=1)` and default lightness range.

**Type changes.**

```ts
type LightnessCurve =
  | { kind: "power"; gamma: number }
  | { kind: "sigmoid"; steepness: number; midpoint: number }
  | { kind: "bezier"; p1: [number, number]; p2: [number, number] };

interface CubehelixParams {
  // ... existing fields, except remove `gamma`
  lightnessCurve: LightnessCurve;
  // keep lightnessMin, lightnessMax, reverse, etc.
}
```

Migration: `DEFAULT_CUBEHELIX_PARAMS.lightnessCurve = { kind: "power", gamma: 1 }`.

**URL keys.** `lightnessCurve` (enum: `power | sigmoid | bezier`), `gamma`, `sigmoidSteepness`, `sigmoidMidpoint`, `bezier1`, `bezier2`. The non-relevant params for the chosen curve are omitted on encode. Default omission still applies.

**UI.** Replace the single "Lightness Curve" slider in [ParamControls.tsx](apps/web/src/components/ParamControls.tsx) with a curve-type selector (radio or dropdown) that swaps in the appropriate parameter controls. The bezier curve probably wants a small inline curve editor (drag two handles in a 2D box) rather than four sliders.

**Python parity.** Mirror the new types in `cubehelix.py` (use a Union of dataclasses or a kind discriminated union). Update the Python parity test's camelCase→snake_case translator to handle the new keys and nested values. The fixture generator must include curve-type probes (one entry per curve kind with non-default parameters).

**Saturation cap.** `saturationCap` currently uses `Math.pow(u, gamma)` directly — refactor it to call the same shared lightness-curve evaluator so it stays consistent.

**Tests.** Default-collapse identity (power γ=1 produces same output as before). Sigmoid monotonicity (output values are non-decreasing). Bezier monotonicity (with valid handles). Endpoints always map to `lightnessMin`/`lightnessMax`. Round-trip URL state with each curve type. Parity fixture passes after regen.

**Files.** `packages/core/src/cubehelix.ts`, `packages/core/src/types.ts`, `packages/core/tests/cubehelix.test.ts`, `packages/python/src/cubehelix_studio/cubehelix.py`, `packages/python/tests/test_cubehelix.py`, `apps/web/src/components/ParamControls.tsx`, `apps/web/src/lib/url-state.ts`, `apps/web/src/lib/url-state.test.ts`, `scripts/generate-parity-fixture.ts`, `fixtures/parity.json`.

## Stage 2b — Chroma envelope shaping

**Goal.** Generalize the chroma amplitude envelope `f · (1 − f)` (peaks at `f = 0.5`) into a tunable curve with adjustable peak position, width, and floor. Lets users push peak chroma into the shadows (heat-map style), narrow or broaden the chromatic mid-tones, or keep nonzero chroma at the endpoints (relevant when `lightnessMin > 0` or `lightnessMax < 1`).

**Math.** Current: `amp = saturation · f · (1 − f) / 2`. New:

```text
shape(f)  = f^a · (1 − f)^b                                   // beta-like profile
peak_f    = a / (a + b)                                       // location of shape peak
norm      = max value of shape over f ∈ [0, 1]
envelope  = (1 − chromaFloor) · shape(f) / norm + chromaFloor
amp       = saturation · envelope · (peak amplitude calibration constant)
```

Parameters expressed in user-friendly terms:

- `chromaPeak ∈ [0, 1]`: peak fraction location, default `0.5`. Internally: choose `a + b = some_function(width)` and `a = peak · (a + b)`, `b = (1 − peak) · (a + b)`.
- `chromaWidth ∈ (0, ∞)`: peak sharpness/width. Default `1`. Smaller → narrower peak. Internally: `a + b = 2 / chromaWidth` (or similar — pick a mapping that gives the original `f·(1−f)` profile when `peak=0.5, width=1`).
- `chromaFloor ∈ [0, 1]`: additive base envelope at endpoints. Default `0`. With a non-default lightness range it lets endpoints retain hue.

**Calibration constant.** Choose the constant so that at `(peak, width, floor) = (0.5, 1, 0)` the formula collapses to `saturation · f · (1 − f) / 2` (the original). That is, peak amplitude calibration `= 0.5 · norm` (since `f·(1−f)/2` peaks at `0.125`; `shape(0.5) = 0.25`; ratio `0.5`).

This is the peak-normalized approach the user previously approved. Numerically identical to today at defaults, so existing palettes and the parity fixture's default-shape entries are unchanged.

**Type changes.**

```ts
interface CubehelixParams {
  // ...
  chromaPeak: number;   // default 0.5
  chromaWidth: number;  // default 1
  chromaFloor: number;  // default 0
}
```

**URL keys.** `chromaPeak`, `chromaWidth`, `chromaFloor`. Default omission.

**UI.** Add three sliders or a small "Chroma" section in `ParamControls.tsx`. Bounds: `chromaPeak [0, 1]`, `chromaWidth [0.1, 5]` (or similar log-scaled), `chromaFloor [0, 1]`.

**Saturation cap.** This is where it gets interesting. The current `saturationCap` percentile-of-S-exit math implicitly assumes the standard envelope. With shape parameters changed, the per-sample S_exit formula changes:

```text
At each u: amp(u) = saturation · envelope(u) · K
For each channel: channel = fraction + amp · direction_component
S_exit_channel = (1 − fraction) / (envelope · direction_positive · K)   // for rising channels
                or fraction / (envelope · direction_negative · K)        // for falling channels
```

So `S_exit` scales as `1 / envelope(u)`. The 95th-percentile cap depends on the envelope shape. Recompute by passing the new envelope into the cap calculation.

**Note on saturation slider calibration.** The peak-normalized calibration means the saturation slider's meaning shifts subtly: today it scales the literal `f·(1−f)` envelope; after this it scales relative to the original peak amplitude after envelope normalization. Numerically identical at defaults, so URL state stays compatible.

**Python parity.** Mirror in `cubehelix.py`. Fixture probes for non-default `(peak, width, floor)`.

**Tests.** Defaults collapse to current math (parity). Envelope is monotonically increasing then decreasing with single peak at `chromaPeak`. With non-default `chromaFloor` and lightness range covering `[0, 1]`, endpoints have non-zero chroma. Saturation cap recomputes correctly.

**Files.** Same set as Stage 2a, plus the `saturationCap` implementation in `cubehelix.ts`.

## Stage 2c — Saturation range along the curve

**Goal.** Independent saturation values at the start and end of the curve, with linear interpolation in between. Davenport's Python port has this (`minSat`, `maxSat`) and it's the only field-standard knob we don't yet expose.

**Relationship to 2b.** `chromaFloor` from Stage 2b lifts the envelope at both endpoints symmetrically. `saturationMin`/`saturationMax` is a different control: it lets one end be more saturated than the other along the whole curve. The two compose — `chromaFloor` controls how much chroma reaches the lightness extremes, while `saturationMin`/`saturationMax` controls how the overall saturation level varies from start to end.

**Math.**

```text
saturation(t) = lerp(saturationMin, saturationMax, tEff)
amp(t) = saturation(t) · envelope(t) · K
```

When `saturationMin === saturationMax === saturation`, math collapses to the current single-saturation form.

**UI affordance.** Single `saturation` slider by default. A small "split" toggle (icon button or chevron) reveals `saturationMin` / `saturationMax` and decouples them. Toggling back collapses to a single value (use the average of the two, or the previous unified value if remembered). Keep the default UI tidy.

**Type changes.** Two options, pick the simpler:

```ts
// Option A: always store both, collapsed when equal
interface CubehelixParams {
  saturationMin: number;
  saturationMax: number;
}

// Option B: keep `saturation` plus optional split overrides
interface CubehelixParams {
  saturation: number;
  saturationMin?: number;
  saturationMax?: number;
}
```

Recommend Option A internally (cleaner math, no special-casing), with the UI presenting a single value when `min === max`.

**URL keys.** `saturationMin`, `saturationMax`. Both default-omitted; emit only when `min !== max` OR when either differs from the default `saturation`. Round-trip with the existing single-`saturation` URL still works (decodes to `saturationMin = saturationMax = saturation`).

**Python parity.** Mirror in `cubehelix.py`. Fixture probes for split-saturation cases.

**Saturation cap.** The cap currently assumes a single `saturation` scalar applied uniformly; it needs to take the worst case across `t ∈ [0, 1]` once saturation varies along the curve. Pass `max(saturationMin, saturationMax)` into the cap envelope calculation, or compute the cap per-sample and take the worst case.

**Tests.** Defaults collapse to current. Endpoints respect `saturationMin`/`saturationMax`. URL round-trip with split and unified forms. Saturation cap covers the worst-case end.

**Files.** Same set as 2a/2b.

## Stage 2d — Hue waypoints

**Goal.** Let the user say "the hue at `t = 0.2` should be magenta, and the hue at `t = 0.8` should be teal" and have the tool back-solve `start` and `rotations` to satisfy those constraints. Two waypoints fully determine the two parameters.

**Math.** The cubehelix angle at a given t is `angle(t) = 2π · (start/3 + rotations · tEff + 1)`. Hue at t is determined by `angle(t) mod 2π`. Given two waypoints `(t1, hue1)` and `(t2, hue2)` (where hue is a target cubehelix angle, not an HSL hue):

```text
angle1 = 2π · (start/3 + rotations · t1 + 1)   ≡ hue1 (mod 2π)
angle2 = 2π · (start/3 + rotations · t2 + 1)   ≡ hue2 (mod 2π)
```

Subtracting: `2π · rotations · (t2 − t1) ≡ (hue2 − hue1) (mod 2π)`.

This admits multiple solutions for `rotations` differing by integer cycles (`+2π · n / (t2 − t1)` for any integer n). The user must pick which "winding" they want — pick the rotation count closest to a current/default value, or expose it as a "winding" integer alongside the waypoints.

**Mapping hue picker → cubehelix angle.** The hue wheel in `StartingHueWheel.tsx` already maps `start ∈ [0, 3]` (or angle in 2π units) to a 2D ring color. Reuse the same picker for waypoints; each waypoint emits a target angle.

**Type changes.** Decide whether waypoints supplement or replace `start`/`rotations`:

- Supplement: `hueWaypoints?: { t: number; angle: number }[]`. When present, `start` and `rotations` are derived from waypoints (existing fields become read-only, or are recomputed when waypoints change).
- Replace: introduce a `hueMode: "freeform" | "waypoints"` field; in waypoint mode, `start`/`rotations` are derived.

Mode toggle preferred.

**URL keys.** `hueWaypoints` as comma list `t1:hue1,t2:hue2,...`, plus a `windingChoice` integer if needed. Presence overrides `start`/`rotations`.

**UI.** Two waypoint rows under the existing wheel. Each row has a t slider and a hue picker (small wheel or color swatch with a click-to-edit). Computed `start` / `rotations` are shown as read-only. Possibly a "winding" selector to pick among integer-shifted solutions.

**Solver.** Two-equation system, closed-form. Care for the modular arithmetic (`hue2 − hue1` should land in `[−π, π]` before computing rotations).

**Tests.** Round-trip: setting waypoints, computing `(start, rotations)`, evaluating cubehelix at the waypoint ts should yield the requested angles within numerical tolerance. Multiple windings produce visibly different curves but all satisfy the waypoint constraints.

**Files.** `packages/core/src/cubehelix.ts` (or a new `packages/core/src/waypoints.ts`), web `ParamControls.tsx` and a new `HueWaypointRow.tsx` or similar, URL state, tests. Python may not need a mirror if this is purely a UI-side computation that produces standard `(start, rotations)` — but if you keep waypoints in the params object, Python needs the same field.

## Stage 2e — Curated preset gallery

interface Preset {

## Stage 2f — Perceptual previews

**Goal.** Let the user check that a palette survives grayscale and the major colour-vision-deficiency conditions without leaving the app. Cubehelix is robust under these by design; we should show the proof.

**Implementation.** A single "Preview as" radio control:

- Normal (default)
- Grayscale (sRGB-luma reduction)
- Protanopia
- Deuteranopia
- Tritanopia

The active preview transforms the rendered swatches, gradient strip, and (probably) the cube tube colours uniformly so all three views move together. The transform is a per-pixel function `RGB → RGB` applied at render time; the underlying palette and URL state are unchanged.

**Math.**

- Grayscale: standard sRGB-luma reduction, `Y = 0.2126·R + 0.7152·G + 0.0722·B` after linearizing, then back to sRGB.
- CVD: Brettel/Viénot transform (well-documented, widely used). One 3×3 matrix per condition applied in linear-RGB space. A `cvd.ts` module in `packages/core` exports the three transforms; the web app applies them on render.

**UI.** Radio group placed alongside the existing palette views — likely a horizontal segmented control above or below the gradient strip. Selection is purely a view setting, not a palette parameter, so it does not enter the URL state.

**Python.** Mirror the `cvd` module so the Python library can apply the same transforms (useful for matplotlib figure previews).

**Tests.** Normal preview produces unchanged colours. Grayscale preview produces equal R=G=B per swatch. CVD transforms are deterministic and reversible to round-trip identity within tolerance.

**Files.** `packages/core/src/cvd.ts` (new), `packages/python/src/cubehelix_studio/cvd.py` (new), `apps/web/src/components/PreviewControl.tsx` (new), plumbing in `GradientStrip.tsx`, `SwatchRow.tsx`, `CubeVisualization.tsx`. No URL-state changes.

## Stage 3 — Diverging cubehelix

**Goal.** Two-sided palette where lightness rises from a lower extreme to a midpoint pivot, then falls back to an upper extreme (or vice versa). Each half is a cubehelix with potentially different rotation count. Examples: red-to-white-to-blue with hue rotations on each side. None of the surveyed cubehelix implementations ships diverging; this is a differentiator.

**Math.** Define a `pivot ∈ (0, 1)` t-value. For `t ∈ [0, pivot]` use one cubehelix from `(start, rotationsLower)` with lightness from `lightnessLower` to `lightnessPeak`. For `t ∈ [pivot, 1]` mirror: lightness from `lightnessPeak` back down to `lightnessUpper`, with hue from `startUpper` (often `start + offset`) and `rotationsUpper`.

Several flavors are possible:

- Symmetric: same rotations both sides, same outer lightness, hue mirrors around the pivot.
- Asymmetric: each side has independent rotations, lightness extents, and possibly different starting hues.

Recommend asymmetric for flexibility, with optional "symmetric" preset.

**Mode.** Add a top-level `mode: "sequential" | "diverging"`. In diverging mode, expose new fields and hide `lightnessMin`/`lightnessMax` (which become per-half) and `rotations` (which becomes `rotationsLower` / `rotationsUpper`).

**Math (concrete suggestion).**

```text
diverging:
  if t ≤ pivot:
    s = t / pivot                     // 0 .. 1 within lower half
    apply cubehelix with:
      rotations = rotationsLower
      lightness range = [lightnessLower, lightnessPeak]
      curve = lightnessCurveLower (defaulting to mirror of upper)
      start = start
  else:
    s = (t − pivot) / (1 − pivot)     // 0 .. 1 within upper half
    apply cubehelix with:
      rotations = rotationsUpper
      lightness range = [lightnessPeak, lightnessUpper]   // note: descending order if peak > upper
      start = startUpper
```

The lightness range should be configured so the lower half's `t=pivot` evaluates to the peak, and the upper half's `t=pivot` also evaluates to peak — ensuring continuity at the pivot.

For reverse divergence (peak in middle is dark, ends are light), simply swap which extreme is "peak" vs. "outer."

**Type changes.**

```ts
interface CubehelixParams {
  // ...
  mode: "sequential" | "diverging";
  pivot?: number;           // [0, 1], required when mode = "diverging"
  rotationsLower?: number;  // when diverging
  rotationsUpper?: number;  // when diverging
  lightnessPeak?: number;   // when diverging
  lightnessLower?: number;  // when diverging (renames lightnessMin)
  lightnessUpper?: number;  // when diverging (renames lightnessMax)
  startUpper?: number;      // when diverging; defaults to start + 0.5 (180° offset) if absent
}
```

Keep the `mode = "sequential"` path 100% backward compatible (use existing `rotations`, `lightnessMin`, `lightnessMax` etc.).

**URL keys.** `mode`, plus `pivot`, `rotationsLower`, `rotationsUpper`, `lightnessPeak`, `lightnessLower`, `lightnessUpper`, `startUpper`. Default-omitted in sequential mode.

**UI.** A mode selector at the top of `ParamControls.tsx`. In diverging mode, the panel reorganizes to show both sides' parameters. Consider a visual "fold" indicator on the gradient strip showing the pivot.

**Saturation cap.** Recompute per-half (each half has its own envelope and lightness range) and take the worst-case cap.

**Cube viz — two-cube layout.** In diverging mode, render two RGB cubes positioned so each half's pivot point coincides at a single shared location in world space. Each cube extends back toward its own dark-corner endpoint. The two helix-tube paths meet at that shared point, making the divergent structure read at a glance.

- Anchor point: `(lightnessPeak, lightnessPeak, lightnessPeak)` if `startUpper - start` keeps the pivot near the diagonal; in general, the pivot's actual RGB coordinates from the cubehelix evaluation.
- If `lightnessPeak = 1`, the shared point is the white corner of both cubes (clean visual).
- For any other peak, the shared point is interior and the cubes overlap geometrically. That's fine and arguably informative — the overlap region is where both halves can reach the same colours.
- Optional "anchor mode" toggle: shared-point view vs. side-by-side view, in case users find the overlap confusing.
- Each cube's wireframe and gamma-axis indicators render independently; the helix tube is two segments (lower half + upper half) meeting at the anchor.

**Gamma bar.** The lightness ramp visualization (`GammaBar`) needs to show the diverging shape (rises to peak, falls back).

**Gradient strip.** Render normally — the diverging palette is still a `t ∈ [0, 1]` ramp, just one whose lightness profile is non-monotonic.

**Tests.** Sequential mode is unchanged. Diverging mode: continuity at pivot (cubehelix output approaches the same value as `t → pivot` from below and above). Endpoints respect `lightnessLower`/`lightnessUpper`. Hue waypoints (if combined with diverging) — out of scope for now, document as future work.

**Files.** Pretty much everything: core math, types, defaults, URL state, `ParamControls`, `GradientStrip`, `GammaBar`, `CubeVisualization` (sample generation + two-cube layout), Python mirror, fixture generator, all tests.

## Deferred / out of scope

These came up in the field-survey of other cubehelix implementations; documenting the decision so future contributors don't relitigate.

- **Oklab / CIELab perceptually-uniform reformulation.** A second curve family where lightness is monotonic in perceptual space rather than BT.601 luma. Substantial scope (new helix coefficients, new gamut-cap math, new parity entries, deciding whether it's a parameter or a sibling function). Deferred as a possible Stage 4. Worth revisiting if user demand surfaces.
- **First-class Cubehelix colour space** (RGB ↔ cubehelix coordinates, `.brighter()`/`.darker()`, opacity channel — d3-style). Different framing from "design a palette, then export"; would inflate the API surface significantly.
- **Per-channel RGB→luma weight tuning** (Thies's `wr`/`wg`/`wb` with NTSC/PAL/HDTV presets). Scientific-imaging niche; off-mission for a UI palette tool.
- **Split gammas** on rotation rate and amplitude (Thies `gamma_rot`, `gamma_amp`). Once Stage 2a lands, the curve selector and Stage 2b chroma controls cover the same design space more cleanly.
- **Per-channel helix distortion** (Thies expert mode `kr/og` etc.). Explicitly experimental even in the original.
- **d3-style "interpolate between two arbitrary colours through cubehelix"**. Different framing; users who need it can reach for d3.

## Cross-cutting expectations for any agent picking this up

- Read the current `cubehelix.ts` and `cubehelix.py` first; the math is short and there are subtle invariants (e.g. the `tEff`-based angle, the lightness range remap as a sub-arc of the underlying full helix).
- Before changing math: write a numeric test that exercises the change, then implement, then regenerate the parity fixture (`pnpm fixture:gen`).
- Keep `DEFAULT_CUBEHELIX_PARAMS` such that defaults reproduce the existing visual output bit-for-bit on the parity fixture's existing entries. New fixture entries should be ADDED for new parameters, not modify existing ones.
- URL state encoding: every new field must omit-on-default and round-trip via the existing `encodeAppState`/`decodeAppState`.
- All changes must keep all three test suites green: `pnpm -F @cubehelix-studio/core test`, `pnpm -F web test`, and `(cd packages/python && uv run pytest)`. Plus `pnpm typecheck` and `pnpm build`.
- Don't credit Claude in commit messages. One-line commit messages unless told otherwise. Don't use `--no-verify`.
- The wheel work is uncommitted on main — coordinate or rebase before touching `ParamControls.tsx`/`App.tsx`/`StartingHueWheel.tsx`/hue-control CSS.

## Recommended execution order

1. **Stage 2a** (lightness curve generalization). Smallest math change with clear scope. Establishes the pattern of "param refactor + URL state + UI selector + Python parity + fixture probes."
2. **Stage 2b** (chroma envelope shaping). Builds on the same patterns; biggest math impact (saturation cap recompute).
3. **Stage 2c** (saturation range along the curve). Piggybacks on 2b's parity work; closes the only field-standard gap.
4. **Stage 2d** (hue waypoints). Mostly UI + small solver. Should land after the in-flight starting-hue wheel commits.
5. **Stage 2e** (preset gallery). No math; quick UX win that strengthens positioning. Slot in any time after 2a–2c are stable.
6. **Stage 2f** (perceptual previews). Pure rendering work; can land independently of any math stage. Substantiates the "survives grayscale, colorblindness, and print" claim in the README.
7. **Stage 3** (diverging cubehelix). Largest restructuring; do last. Two-cube cube-viz layout is the headline visualization.

Stages 2e and 2f are independent of the math stages and can land at any point — useful low-risk inserts while bigger work is in flight. Stage 2f's CVD module should also be applied to the diverging palettes once Stage 3 ships.

Each stage should be a single logical commit (or commit pair: math/types + UI). Validate parity after each.
